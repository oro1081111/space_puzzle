# ATLAS-R 路線教師：訓練與驗收紀錄

日期：2026-09-22。範圍：15×15 / 30×30，三人局。

## 結論與發布狀態

本輪實作了風險感知路線參數訓練、隔離狀態的多局面 rollout、完整對手／座位評估。
這是黑箱策略參數最佳化，不是完成新的 PPO / MAPPO 神經網路訓練。
15 階 v7 快速候選已通過標準開局 540 局的強度門檻，並完成本機網頁 Worker 整合；但隨機中盤接手出現退步。
30 階仍未通過強度門檻。因此整體目標未完成，`release_approved: false`。
訓練結束時原先未發布；使用者其後明確要求「直接先幫我推上去，讓我玩玩看」，因此改為實驗試玩發布。
`release_channel: experimental` 與 `experimental_publish_authorized: true` 只表示試玩授權，不表示通過正式版驗收。
本次僅在 15×15 三人局啟用 Route v2，保留弱點提示；其他模式及 ONNX 模型未更換。下列驗收結果不因試玩發布而更改。

## 為什麼改方法

先確認能產生可靠的強決策，再訓練網路模仿它。把弱搜尋教師的資料量加大，無法保證變強。
依 ponytail 的最小實作原則，直接重用實際網頁引擎與既有多步路線，不另造遊戲規則或加訓練框架。

本輪測試的變因：

1. 路線遭搶風險：用對手到達的曼哈頓下界與路線步數衡量風險，並非偷看實際意圖。
2. 困敵分數：扣除原本已受困和普通路徑佔格造成的部分，避免重複獎勵；仍是近似評分。
3. 候選路線：既有 beam 路線、直切／單彎切割，以及不同邊界、空間、長度權重。
4. 黑箱參數訓練：族群隨機變異、局部座標搜尋，包含最弱配對／座位目標。
5. 長搜尋：保留可執行路線，模擬所有九種有序舊策略組合；只從公開局面重建對手，不讀對手私有規劃。

## 評估方法

每個完整驗收為 20 種子 × 9 有序對手配對 × 3 座位 = 540 局。
三種舊策略可重複配對，所以包含 APEX+APEX、BASTION+BASTION、SWEEP+SWEEP。
「勝」指單獨第一，平手另列，未終止不能算勝。固定開局，種子改變策略內部隨機選擇。
不代表測過所有中盤局面或人類策略；隨機前綴與真實瀏覽器仍是另外的發布關卡。

門檻：整體至少 70%，每個座位與每種對手配對均高於 50%，未完成 0 局。
不因結果接近門檻就事後降低標準。觀察過的驗收集不得再當下一版的全新留出集。

  這是小樣本配對對照，不是 540 局現行模型勝率。

## 作廢實驗與修正

1. 最初 teacher 實驗沿用了前次固定動作 callback，導致重新規劃時無動作。
   已在私有狀態複製時還原真實 AI callback，並補回歸測試。
   `teacher15-pilot24`、`teacher15-dev24`、`teacher15-expanded90-pilot`、`teacher15-topcuts120-pilot` 作廢。
2. 規劃種子曾由實戰種子衍生，可能讓假想對手與真實對手 tie-break 相關。
   改成獨立的 `101 + 成功回合 * 31`，另測相同公開棋盤在不同實戰 RNG 下選擇一致。
   所有此前長搜尋數字都不能當發布證據，包括 `teacher15-heldout20`，後者已停止並保留紀錄。
   **不受影響**：全部純路線參數訓練與上述 `route*` 驗收，不走 teacher rollout。
3. 初版 Windows 低優先權設定的 HANDLE 型別有錯，已修正並驗證 Python / Node 為 BelowNormal。
   不宣稱修正前整段執行都是低優先權，也未量測筆電溫度。

- 15 混合候選的低成本版（80 回合／3 情境）：53/81（65.4%），1 平；APEX+APEX 與 BASTION+BASTION 均只有 4/9。
  同樣三種子下，純路線為 48/81（59.3%）。不能用另一組較好看的種子勝率直接相減當搜尋增益。
- 15 完整混合搜尋（120 回合／9 情境，獨立 RNG）：60/81（74.1%），1 平；最弱座位 16/27、最弱配對 5/9，未終止 0。

- 15 混合路線的三個完整對局已逐步核對 Python / JS 規則一致，這只是正確性檢查，不能以 3/3 當成強度證據。
- 開局書 v5 / v6：整條候選路線均不如無開局書，兩版都選回原策略，開發驗證 50/81。
- 15 短開局 v7：87 個候選／座位評分，學到第三座位先往下兩步，再交回動態策略。
  開發驗證 56/81，第三座位 25/27；依這項改善追加全新 540 局，得到上述 392 勝。
- 30 短開局 v6：33 個候選／座位評分，開發驗證 57/81，但正式 540 局只有 367 勝，未採用。
- 中盤公開幾何條件切換：尚未取得邊界領地時改用 APEX / SWEEP 或無神經網路的反應式搜尋。
  開發集分別 29/81、29/81、27/81；APEX 補丁在全新中盤測試仍落後現行版，故本機 Worker 恢復未加此補丁的 v7。

前九輪路線訓練共 12,717 場計分候選對局；加上四輪開局實驗的 4,131 場，共 16,848 場計分候選對局，
不含開發驗證、留出集、未納入該座位評分的額外控制局與 teacher 內部 rollout。
同一組種子重複用來比較候選，不代表 16,848 個獨立統計樣本；這也不是神經網路訓練步數。

搜尋新增可選的 `--prune`：每個情境分數上界為 1.1，只在候選的剩餘最佳可能值仍低於已完整評估的最佳候選時跳過。
不是減少對手類型，也不是近似剪枝。被剪掉的候選分數是上界，不能當蒸餾標籤。
三場完整 Python / JS 回放的得分與終止嘗試數均和不剪枝一致；模擬嘗試數由 32,563 降至 27,902（少 14.3%）。
牆鐘時間受同時執行的工作影響，不把這三局的時間差當可靠瀏覽器效能數字。

## 正確性檢查

- Python unittest：23 項通過，含候選 cuts / beam 路線完整對局的規則一致性、搜尋隔離、獨立 RNG、剪枝選擇一致、開局書與生成 Worker 一致性及發布門檻。
- Node：`atlas.test.cjs` 與 `collision.test.cjs` 通過；包含既有 160 個搜尋一致性案例。
- 相同九場案例，單工與三工作程序的結果完全相同。
- 新增的快照 Oracle 已實測平行執行，子程序使用相同來源快照。
- 實際 Codex 瀏覽器：三個 Route v2 自弈正常結束，棋盤填滿，得分 93 / 102 / 30。這是本機瀏覽器證據，不是線上部署證據。
- 既有完整瀏覽器測試被舊版 ONNX 的外部 jsDelivr runtime 載入失敗阻擋，未宣稱全套通過。新 Route Worker 不依賴該 CDN。
- 尚無完整瀏覽器 P50/P95 延遲報告，也未做公開站部署驗證。

## 重現與資料

### 後續決策順序，不以無限加訓練取代驗收

1. 先完成本輪有界實驗。只有開發矩陣整體達 70%、各席與各配對高於 50%，才花成本做新 540 局驗收；不從最終驗收局挑參數。
2. 若快速路線候選通過：先直接接 Worker，不強制改成神經網路。測真實瀏覽器 P50/P95/最大延遲、重新開始取消、三個 ATLAS 自弈和碰撞終局，確認 UI 不被阻塞。
3. 若只有慢搜尋通過：蒸餾「候選路線優劣」，而不是直接複製四方向動作。保存每個公開局面、所有候選路線、九情境實際終局分數；保留敗局和各座位，不只收集勝局。
4. 使用已有 PyTorch 做小型路線排序器：棋盤通道＋自身／對手頭部＋候選路徑遮罩＋路徑長度／風險特徵。以實際 rollout 候選分數訓練排序／Value，不把啟發式評分當正解。
5. 以完整對局／種子分割 train/validation/test，不把同局相鄰回合拆到不同集合。先檢查候選排序準確度，再跑完整遊戲；方向準確率不能代替勝率。
6. 蒸餾版對比教師、快速路線、現行 ATLAS 與三種舊策略；只把弱點局面交回搜尋擴充資料。資料增加前先測這批新標籤是否真的改善留出的決策。
7. 只有教師品質與蒸餾保留率都成立，才加入 league 自我對弈；否則先改候選路線覆蓋或估值，不反覆訓練同一個弱教師。

路線候選訓練、部分 Worker 整合、隨機前綴測試已執行，結果如上；神經網路蒸餾、league 再訓練與正式發布尚未完成。
下一輪重點是中盤路線選擇與 30 階第二座位，不是繼續只堆標準開局的對局數。四人局未做新版強度驗收。

### 執行與查核入口

實作入口詳見 `TEACHER_PLAN.md`。每次執行保留 config、來源快照、權重、逐局 JSONL 與摘要。
大量 `training/runs/` 檔案受 .gitignore 排除，仍保留本機；發布前須另保存選定候選與必要證據。
